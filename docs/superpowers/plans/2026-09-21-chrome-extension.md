# Chrome Extension Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Снять страницу, на которой пользователь сейчас находится, в пяти брейкпоинтах и отдать файл `.w2f`, который принимает плагин из плана 5.

**Architecture:** Расширение MV3. Фоновый воркер управляет размерами через CDP-эмуляцию, впрыскивает уже существующий сериализатор в страницу, собирает пять экранов с общей нумерацией, **сам** забирает байты изображений (обходя CORS страницы), пакует бандл и отдаёт его через `chrome.downloads`.

**Tech Stack:** тот же воркспейс; `chrome.debugger` (CDP), `chrome.scripting`, `chrome.downloads`, `fflate` через `@w2f/bundle`.

**Место в карте планов:** план 6 из 7. Дальше: 7 — компоненты, токены и auto-layout.

## Три замера, сделанных до написания плана

### 1. Расширение проверяемо целиком

Playwright умеет поднимать MV3-расширение в **новом** headless, и фоновому воркеру доступны `chrome.debugger`, `chrome.scripting`, `chrome.downloads`.

```
новый headless:   РАБОТАЕТ {"debugger":true,"scripting":true,"downloads":true}
обычный headless: service worker не поднимается вовсе
```

Это главное для плана. Половина проекта, которую нельзя проверить, у нас уже есть — плагин Figma, — и второй такой быть не должно. Расширение держится того же стандарта, что и всё остальное: измерено, а не заявлено.

**Следствие для тестов:** `--headless=new` обязателен в аргументах, иначе расширение просто не загрузится, и тест упадёт с невнятным таймаутом ожидания воркера.

### 2. CDP-эмуляция действительно меняет вьюпорт

```
просили 1440×900 → {"dir":"row",    "inner":1440}
просили 390×844  → {"dir":"column", "inner":390}
```

Медиазапросы применились: флекс-ряд стал колонкой. Значит режим A из спеки работает, и подменять его изменением размера окна не нужно.

### 3. Фоновый воркер обходит CORS страницы

Тот же URL, два контекста:

```
со страницы (origin 4317 → 4318): ОТКАЗ: TypeError: Failed to fetch
из фонового воркера расширения:   ok, 195 байт, image/png
```

**Это меняет проект, а не только план.** В плане 4 кросс-доменная картинка была продиагностированной потерей: она отрисовывается, значит узел строится, а байты не приходят, и узел становится заглушкой. В жизни это доминирующий случай — любая картинка с чужого CDN. Расширение с `host_permissions` его закрывает.

Поэтому фаза разрешения ассетов **переезжает из страницы в воркер**. Граница, проведённая в плане 4 ради синхронности обхода, оказывается ровно той, которая нужна и здесь: обход остаётся в странице, байты забирает воркер.

## Что остаётся риском

**`chrome.debugger` показывает пользователю жёлтую плашку** «расширение отлаживает этот браузер». Убрать её нельзя — это защита Chrome, и это правильно. Для командного инструмента без публикации приемлемо; в README это должно быть написано прямым текстом, а не обнаружено пользователем.

**Отсоединение отладчика обязано быть в `finally`.** Если воркер упадёт между `attach` и `detach`, вкладка останется с подменёнными метриками и плашкой, и починить это можно будет только перезагрузкой. Это не гипотеза: у `Emulation.setDeviceMetricsOverride` нет автоматического срока годности.

## Правила, унаследованные от планов 1–5

**TDD.** Тест первым, запуск, падение по ожидаемой причине, потом реализация.

**Проверяй проверки.** За пять планов семнадцать проверок оказались негодными. Последний случай (17) добавил правило, прямо относящееся к этому плану: **проверка, про которую заранее известно, что она чего-то не видит, обязана быть дополнена другой проверкой, а не оговоркой.**

**Пороги не подгоняются.** Дважды в плане 4 это спасло гейт от превращения в пустой.

**«Ноль расходящихся пикселей» везде означает «ноль, не считая сглаживания»** — у гейта `includeAA: false`. Измерено на сверке с Figma: скрытая часть это 0.025% изображения.

**Коммиты** заканчиваются трейлером:

```
Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
```

### Task 1: Каркас и подъём расширения в тесте

**Files:** `packages/extension/{package.json,tsconfig.json,tsup.config.ts,manifest.json}`, `src/worker.ts`, `tests/e2e/extension.spec.ts`

- [ ] **Step 1: Падающий тест — расширение поднимается.**

```ts
test('расширение поднимается и видит свои разрешения', async () => {
  const { context, worker } = await launchWithExtension()
  const granted = await worker.evaluate(() => ({
    debugger: typeof chrome.debugger?.attach === 'function',
    scripting: typeof chrome.scripting?.executeScript === 'function',
  }))
  expect(granted).toEqual({ debugger: true, scripting: true })
  await context.close()
})
```

Хелпер `launchWithExtension` обязан передавать `--headless=new`. **В комментарии написать почему:** без него воркер не поднимается вовсе, и тест падает таймаутом ожидания события, из которого причина не видна.

- [ ] **Step 2: Запустить, убедиться в падении** (пакета ещё нет).

- [ ] **Step 3: Завести пакет.** Манифест: `manifest_version: 3`, разрешения `debugger`, `scripting`, `activeTab`, `downloads`, `host_permissions: ["<all_urls>"]`.

`<all_urls>` — не перестраховка: без него воркер не сможет забрать картинку с чужого домена, то есть пропадёт вся выгода из замера 3. В README это должно быть объяснено.

- [ ] **Step 4: Сборка `tsup`, платформа БРАУЗЕР.** Та же ловушка, что в плане 5: под платформу Node `fflate` тянет `require("module")`, которого в воркере нет.

### Task 4: Байты изображений забирает воркер

**Files:** `src/assets.ts`

Главная выгода расширения.

- [ ] **Step 1: Падающий тест.** Фикстура `image-cors`: узел ссылается на картинку с порта 4318. В бандле, собранном расширением, ассет обязан **присутствовать**, а узел остаться `kind: 'image'`, а не стать заглушкой.

Это ровно тот случай, который в плане 4 был продиагностированной потерей. Тест обязан явно сравнивать с поведением `capture.mjs`, где ассета нет.

- [ ] **Step 2: Реализовать.** Заявки приходят из страницы (`resolvePendingAssets` больше не вызывается там), байты забирает воркер своим `fetch`.

Нормализация формата и размера требует канвы, которой в воркере нет. `OffscreenCanvas` в service worker **есть** — проверить замером, а не предположить; если нет, нормализация остаётся в странице, а воркер забирает только исходные байты.

- [ ] **Step 3: Слом.** Забирать байты из страницы — тест на `image-cors` обязан упасть.
